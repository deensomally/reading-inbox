## Architecture and ownership

Keep the React/TypeScript/Vite PWA and IndexedDB. Add **one same-origin Node.js/Fastify service with SQLite on a persistent volume** for live mode. Run the poller in that process with a durable due-time table. One instance is sufficient for the proposed personal installation. The static demo can still run on its own.

| Location                   | Owns                                                                                                                                                                                                                                                   | Data flow                                                                                                                                                                                                                                                                                                         |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Publisher                  | RSS/Atom, linked article, published rights and discussion destination                                                                                                                                                                                  | The server requests public feeds. A reader action can request an eligible public article. Opening a publisher link uses the reader’s ordinary browser session.                                                                                                                                                    |
| Private service and SQLite | Per-installation subscriptions and feed membership, validators, last success/error, next poll and lease, observed entry IDs/aliases, metadata, current revisions, permitted bodies, ordered changes. Optional AI adds a scoped cache and spend ledger. | Subscribe/unsubscribe and manual refresh are idempotent commands. The worker commits entry changes, validators and its next schedule atomically. A paged delivery API returns the device’s entries and policy changes. A body endpoint accepts a known article ID.                                                |
| Device and IndexedDB       | Local membership mirror, indexed article metadata, permitted offline bodies and summaries, reading depth/position, saved/archive flags, last applied cursor                                                                                            | On open, resume, reconnect or manual refresh, display the local library immediately and fetch changes since the last cursor. Apply each page and its cursor in one transaction. A stale cursor triggers a paged snapshot at a fixed sequence, then deltas from that sequence. Replays leave reading state intact. |
| Optional summary provider  | One permitted source revision and one explicitly requested depth                                                                                                                                                                                       | Only the private service contacts the selected provider. It sends the allowed passages and instructions and receives a summary.                                                                                                                                                                                   |

The first remote deployment is **single-owner**. Each installation has its own feed set, cursor and access scope, bound to an authenticated session. A second device can import the same OPML if desired. Saved items, reading positions and archive changes stay on each device. This gives future sync a stable model without implementing cross-device sync in Phase 2.

Give SQLite unique constraints for a feed URL alias, an installation’s membership of a feed, and a feed’s item alias. Link each observation to a stable article and its current revision. Keep the installation’s first-received timestamp even if an entry is redelivered. Return changes as ordered upserts and explicit withdrawals with an opaque next cursor. Bound each catch-up to a high-water mark so new arrivals cannot make pagination skip older rows. Represent a publisher’s withdrawal separately from an item disappearing from its feed window.

**Alternatives.** A static PWA is the cheapest demo host. Browser cross-origin rules prevent some feeds from being read, and periodic background sync is scheduled at the browser’s discretion. A public CORS proxy adds a third party that sees reading interests and offers no durable observation history. Managed cron, functions and a hosted database could replace the single process for a larger deployment, at the cost of multiple services, egress controls and backup boundaries. Use the personal service first. Both Substack feeds sampled in Phase 0 omitted an allow-origin header. [Phase 0 observations](../ARCHITECTURE.md#what-we-verified) · [Browser cross-origin rules](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS) · [Periodic background sync](https://developer.mozilla.org/en-US/docs/Web/API/Web_Periodic_Background_Synchronization_API)

### Subscriptions, polling and durable identity

1. **Add a source.** Accept a public RSS/Atom URL, a Substack publication hostname or its home URL. Resolve a Substack publication using the documented `/feed` path. For another publication home page, follow a permitted, advertised RSS/Atom alternate or ask for the direct feed URL. Show the resolved publication and URL. Reject private or credential-bearing URLs in this public-feed phase. Preserve meaningful path and query components. Store redirects as verified aliases so a renamed publication can keep its feed ID. [Substack RSS documentation](https://support.substack.com/hc/en-us/articles/360038239391-Is-there-an-RSS-feed-for-my-publication)
2. **Import every entry the feed supplies.** Parse RSS 2.0 and Atom 1.0 with namespaces, character encoding, relative links and declared base URLs. Capture title, byline, publication, published/updated times, first receipt, categories, canonical post link, explicit discussion link, and available content. Make the stable key a feed-scoped opaque RSS GUID or Atom entry ID. Use a verified article permalink as a secondary alias and for entries without IDs. Never strip arbitrary query parameters or merge items across publishers by headline. For entries with neither stable ID nor link, persist an observation fingerprint to recognise identical replays. An anonymous edited entry may be indistinguishable from a new post. Keep an ambiguous entry visible rather than overwriting another article’s state. [RSS specification](https://www.rssboard.org/rss-specification) · [Atom specification](https://datatracker.ietf.org/doc/html/rfc4287)
3. **Poll while devices are closed.** Propose a 30-minute default with jitter, publisher update hints and per-host concurrency limits. Honour cache directives and use conditional GET with ETag/Last-Modified. A 304 updates check status without touching articles. On valid 200 responses commit all observed entries, including older out-of-order entries. Back off on timeout/5xx, respect Retry-After on 429/503, and pause persistently unavailable or forbidden feeds with a reason, last successful check and a retry/change-URL action. Never advance validators past a failed parse or partial write. Persist due times, use an expiring job lease, and resume overdue work fairly after restart. Manual refresh joins existing work and respects cooldowns. [HTTP validators, conditional requests and Retry-After](https://httpwg.org/specs/rfc9110.html) · [HTTP 429](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)
4. **Retain history.** Removing an entry from a later feed window does not remove its catalog record or its permitted stored body. Unsubscribing stops future collection for that installation, acknowledges the change, and keeps previously delivered articles retrievable with their flags. Re-subscribing reuses the source identity and ingests its current feed. An offline subscription edit is shown as pending until acknowledged. Check membership when committing an in-flight fetch so a completed unsubscribe cannot admit new entries. First subscription and downtime can only recover entries a publisher still exposes. Show last success and any known gap. Do not promise a complete pre-subscription archive.
5. **Apply edits without moving the reader.** Use a stable article ID across revisions. Hash the canonical ordered body, link targets and relevant media. Track coverage, policy version and summary-relevant attribution separately. An edit can invalidate affected summaries or search terms without touching independent saved, archived, opened, deepest, last-stage or publisher-handoff fields. Keep the original publication/received date for sorting unless the publisher corrects the publication date. Preserve per-stage positions, match a surviving passage anchor after edits and fall back to a bounded offset. Announce a new revision without replacing text underneath an active selection. Losing permission takes effect on receipt of that change.

### Original articles and publisher permissions

Phase 0 found 20 entries in each of two anonymous Substack feeds. Both had HTML in `content:encoded`, yet one entry was a 59-word teaser and another exceeded 6,000 words. In a separately licensed Creative Commons example, all 17 article paragraphs appeared in order in the feed, followed by feed-only boilerplate. A naive first-`article` selector found only one paragraph on the page. These observations justify both a feed-first path and a last-passage check. Substack documents paid preview boundaries, and its terms restrict scraping and substantial copying/storage. Use its syndication endpoint and the browser handoff by default. [Recorded comparisons and sources](../ARCHITECTURE.md#what-we-verified) · [Substack previews](https://support.substack.com/hc/en-us/articles/4407989020308-How-do-I-publish-a-free-preview-of-a-paid-post-on-Substack) · [Substack terms](https://substack.com/tos)

| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Complete, permitted RSS/Atom content           | Prefer publisher-supplied body blocks. Trust a documented full-text source with validated boundaries or a match to the permitted original, including its final substantive passage and important media. Show Original and attribution. Offer one-action **Copy full article text** from any depth when copying is allowed.                                                                                                                                                                                                                        |
| Summary, teaser or uncertain completeness      | Label **Excerpt** or **Completeness unverified**, give the reason and link to the publisher. An Atom summary, an HTML content field, word count or absence of a paywall marker alone cannot establish completeness. Label permitted copy **Copy excerpt**. Only offer an explicitly excerpt-based AI depth when there is enough permitted evidence for it.                                                                                                                                                                                        |
| Public page with permission to extract         | Automatically queue eligible incomplete entries and support owner-requested recovery of history. Fetch the linked article, without cookies. Use a source-specific article boundary where verified and a readability-style extractor otherwise. Compare ordered headings, text, lists, figures and the closing passage against the publisher body. If access, attribution or completeness is uncertain, retain the best labelled permitted preview and hand off. [Readability and safe rendering](https://github.com/mozilla/readability#security) |
| Subscriber-only, blocked, withdrawn or missing | Preserve allowable metadata and a publisher link. Show any separately permitted public preview accurately. Sign-in and entitlements belong to the publisher. Decline unavailable copy or AI actions. A possible future user-selected email would require provenance, consent and its own private scope and coverage check. Mailbox access and email import are separate decisions.                                                                                                                                                                |

Record the basis for each use per source/revision, including licence or publisher permission, scope, attribution, source URL and date reviewed. Distinguish display, local/server retention, copying, export and transmission to a named AI provider. A syndicated description can support an inbox entry even where text reuse is unapproved. When a public edition has no explicit reuse grant, retain eligible text for the owner’s private reading and withhold its portable export and external processing. Explicit restrictions take precedence. Robots directives and platform terms apply to fetching, and publisher/third-party licences govern subsequent uses, including images. Recheck policy before serving, copying, exporting or dispatching AI. On withdrawal, invalidate derived text, search entries, assets and summaries in the service and on the next connected device update. An offline device cannot receive a new restriction until it reconnects. [Robots Exclusion Protocol](https://www.rfc-editor.org/rfc/rfc9309.html) · [Example publisher licensing terms](https://creativecommons.org/terms/)

Render safe structured blocks with ordered inline text, emphasis and links, heading levels, nested/ordered lists, quotes, figures with alt text and captions, tables and code where present. Resolve relative links and preserve passage IDs and order. For allowed images use a bounded, validated fetch or an explicitly enabled publisher load. Provide alt text, captions or the publisher link when assets cannot be used. Drop scripts, forms, tracking pixels and active embeds. Record material omissions as a coverage limitation. Original uses the publisher’s words throughout. Derive plain-text copy from the same blocks, through the final paragraph, with the existing clipboard-denied fallback.

Keep the collapsed **Reader discussion** beneath the complete, permitted Original. Use **View original comments** for a publisher-supplied discussion destination, the same post as the labelled fallback, and the existing disabled/no-link cases. Phase 2 adds no comment ingestion or AI discussion analysis. [Existing behavior](../src/components/ArticleBody.tsx) · [Phase 1 handoff evidence](PHASE_1_REVIEW.md)

### Finding, archiving and exporting articles

- **Chronology.** The default Inbox includes every unarchived subscribed entry, newest publication date first. Fall back to the immutable first-received time with the existing **Received** label. Normalise valid dates to UTC and use stable ID as the final tie-breaker for pagination. Oldest-first reverses the date order. Length sorting uses word count only for known complete text, with unknowns explicitly last in both directions. Optional publication groups keep every matching row reachable.
- **Search and filters.** Index title, author, publication, source categories/topics and permitted collected text locally. Use a paged metadata projection with a rebuildable token index, updated in the same delivery transaction as the revision or policy. Add composable publication, publisher-supplied topic and reading-status filters, with counts and a clear-all action. Entries without tags remain available. Search works offline over collected data. It does not fetch or send articles to a model. Preserve the active collection, filters, list position and focused row on Back.
- **Archive.** Offer selection and archive by date with the scope and exact count shown before applying. “Older than” means strictly before midnight at the start of the chosen date in the device’s time zone, converted to an instant. Freeze matching IDs across pages at confirmation and set archived explicitly in a transaction. Repeating the command keeps the same result. Preserve saved and depth, provide Undo for the affected rows, and keep Archive searchable.
- **OPML.** Preview a bounded OPML 2.0 import, including nested outlines, feed `xmlUrl`, title and optional `htmlUrl`. Report valid, duplicate, invalid, private and unsupported entries individually. Queue accepted subscriptions through the same idempotent path as manual adds. Keep accepted folder labels for OPML round-trip. Export active subscriptions in standard XML with correct escaping. OPML carries the subscription list. [OPML 2.0](https://opml.org/spec2.opml)
- **Saved articles and state.** Offer a separate versioned JSON download. Include stable article/source references, attribution, independent reading flags for all collections and stage/position records. Include a saved body or cached summary only when its specific export rights permit it, with coverage, revision and licence. List any omitted fields and reasons. Exclude credentials, session identifiers and private feed tokens. Provide a local round-trip that matches existing IDs, checks version and current rights, previews conflicts and preserves newer local changes. Export is a user-controlled file, including when they choose to move profiles.

### Optional live progressive summaries

Until real AI is enabled, an explicit first open on a live item keeps the Essence entry point and explains that AI summaries are off. **Read original** and the list’s direct Original shortcut work immediately. An available publisher excerpt is attributed as such. Authored demo summaries apply only to fictional fixtures. When live AI is enabled, ordinary first open requests Essence, explicit More detail requests just the next depth, and reopening restores the last chosen stage.

| Depth         | Source and output contract                                                                                                                                                   |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Essence       | One sentence stating the central claim. Preserve attribution and consequential qualifiers.                                                                                   |
| Brief         | One coherent paragraph adding the principal argument and relevant support.                                                                                                   |
| Understanding | Three substantive paragraphs covering the argument, evidence/reasoning and important caveats or uncertainty. Decline this depth when the available source cannot support it. |
| Original      | Display the permitted publisher revision directly. It is available during timeouts, budget exhaustion or provider downtime and makes zero model calls.                       |

**Generate each requested depth independently from the same source revision.** Send ordered passages with stable IDs and a stage-specific neutral instruction. Ask for supporting passage IDs and validate that they resolve to the current version. Treat publisher text as data. The model has no tools, network access or authority to change state. Render validated text, label the provider-generated stage, and offer passage links where supported. Generating all depths on first open would charge readers for stages they skip. Chaining Brief from Essence and Understanding from Brief loses evidence and can propagate errors. A shared outline could help very long pieces but adds another inference, cost and potential error.

**Long articles.** Count the full permitted input, instructions, evidence IDs and reserved output before dispatch. Proposed initial product limit is 32,000 input tokens per request even if the model accepts more. Above the limit, explain that this depth is unavailable and keep Original accessible. Never silently truncate an article and claim full coverage. If real demand justifies it, evaluate passage-based chunking with a final synthesis, explicit coverage and a separately costed quality gate before enabling it.

**Provider choice.** Benchmark OpenAI GPT-5.4 mini as the baseline already priced in Phase 0. Compare Google’s paid Gemini 3.1 Flash-Lite on the same permission-cleared articles. The former lists a 400,000-token context window and a dated model snapshot. The latter lists a 1,048,576-token input limit and lower text rates. Neither advertised context size nor price establishes faithfulness on these articles. Start with one adapter in production and pin the selected model revision where available. Record the served revision and bump the cache version on upgrades. Local inference avoids sending the article to a provider, but introduces model distribution, memory and latency constraints on Android or a small server. It is a poor dependency for the first live RSS release. [OpenAI model](https://developers.openai.com/api/docs/models/gpt-5.4-mini) · [Gemini model](https://ai.google.dev/gemini-api/docs/models/gemini-3.1-flash-lite) · [Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing#gemini-3.1-flash-lite)

**Privacy.** Obtain explicit opt-in for the named processor. Show what leaves the device and how long the provider can retain it. Send only the eligible article passages and necessary attribution/instructions. Exclude subscriber identities, feed URLs with tokens, history and library state. Keep keys in a server environment secret, outside the browser, exports and logs. For OpenAI use foreground requests with `store: false`, without provider-side conversation state. API data is excluded from training by default, but standard abuse-monitoring logs can retain content for up to 30 days with documented exceptions. Zero Data Retention requires provider approval. Google’s paid API terms exclude prompts/responses from product improvement. Its published abuse-monitoring period is 55 days for prompts, context and output. Recheck the selected endpoint, region and terms at approval. Do not silently switch processors on failure. [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data) · [Gemini paid terms](https://ai.google.dev/gemini-api/terms) · [Gemini abuse monitoring](https://ai.google.dev/gemini-api/docs/usage-policies)

**Cache and billing.** Key successful results by installation/access scope, stable article ID, source revision including relevant attribution, coverage and permissions version, depth, provider/model revision and prompt version. Preserve the demo namespace. Coalesce concurrent browser requests and enforce a unique job/cache key on the service. Recheck rights/revision on cache hits, before dispatch and before committing/serving a response. Request validation includes output shape, passage references and coverage label. Cache only valid, successful results. Discard stale responses. Cache hits, polling and direct Original incur zero inference cost.

Before dispatch, reserve the maximum billed input/output cost in a SQLite transaction against the per-installation and total monthly budget. Cap output including reasoning tokens and settle from reported usage. Count retries against the same limits. A crash or timeout after dispatch can leave the bill unknown. Hold the reservation, reconcile usage and avoid automatic duplicate submissions. Respect provider cooldowns, bound retries on confirmed recoverable failures, and allow an explicit later retry. Show an accessible loading status immediately and keep Original usable throughout. Measure tap-to-validated-text p50/p95 on cold and cached opens. Proposed cold p95 targets are 8 seconds for Essence, 12 for Brief and 20 for Understanding on the test connection. These are review targets, pending measurement.

## Deployment, compatibility and risks

For local review, serve the built PWA and `/api` from one loopback origin, or proxy the API through Vite in development. For an always-on host, use one service supervised by the OS or a single container with a mounted SQLite volume. Put a private HTTPS reverse proxy with owner authentication in front of it. Bind the application to loopback by default, validate Host and Origin, protect state-changing requests against CSRF and use secure, same-site, HTTP-only sessions when hosted. Require authorisation on every subscription, article, asset, job and export read. Keep the server’s writable files out of the static web root.

Upgrade Dexie v1 in place on the existing browser origin, profile, host and port. Add tables/indexes in a new schema version, with defaults for legacy records and a resumable index build. Preserve v1 IDs, body hashes, mock keys, state, positions and routes. Initialise an installation identity only for live mode. Coordinate old tabs and a waiting service worker before migration. A deployment at a different origin cannot read the original database. Provide the local export/restore path for deliberate moves and keep an in-place upgrade path. Roll back the service or disable live ingestion without deleting the library. Test a rollback-compatible reader on the upgraded schema before release. [Phase 1 setup and storage boundaries](../README.md) · [Browser storage and eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

## Decisions for the owner

1. **Approve the RSS-first sequence and hosting boundary.** Recommend milestones 1–3 for the first trial, a single-owner service and 30-minute polling. A local always-on machine is enough to evaluate it. A hosted deployment would need a separate choice of operator, authentication and monthly hosting budget.
2. **Approve the source and retention policy.** The initial pilot shipped in Milestones 3–4. Milestone 7B authorises private feed-first reading, ordinary eligible public page extraction and retrospective recovery. Unknown reuse information permits ordinary private reading subject to the applicable publisher terms. Explicit restrictions and withdrawals take precedence. Keep device state and permitted saved material through unsubscribe.
3. **Decide on external AI separately after the RSS trial.** Select permitted processors, review retention, approve the evaluation corpus and up to $2 for a measured comparison if desired. Choose the production model and a hard monthly ceiling only after seeing the results. The RSS milestones require no AI purchase.

Recommendations and cross-device synchronisation belong to Phase 3. Discussion insights belong to Phase 4. The existing Reader discussion handoff is part of the Phase 2 regression suite. This proposal awaits explicit approval to begin implementation.
