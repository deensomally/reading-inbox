# Reading Inbox architecture

**Phase 0 · 19 November 2026 · Local-first PWA and phased approach agreed. Detailed plan under review.**

Build one installable, responsive progressive web app (PWA) for Android and Windows. The first milestone prioritises a polished four-stage reader with fictitious articles and deterministic summaries. Its AI actions concern the selected article and, when supplied, its reader discussion. The main feasibility constraint is whether a publisher supplies a complete article and permits the requested use. The reader should know what is available before copying text or requesting a summary. ## What we verified

| Question | Evidence and consequence |
| --- | --- |
| What does a public Substack feed deliver? | Substack documents a publication’s `/feed`. Two anonymous RSS requests returned HTTP 200 and 20 entries each. Both included links, GUIDs, bylines, dates and HTML in `content:encoded`. Neither had an RSS `comments` field. One Pragmatic Engineer entry had 59 words and “Read more”. Another had over 6,000 words. Length alone cannot establish completeness. A third request to `on.substack.com/feed` was blocked by the workspace network. [Substack RSS help](https://support.substack.com/hc/en-us/articles/360038239391-Is-there-an-RSS-feed-for-my-publication) · [The Pragmatic Engineer feed](https://newsletter.pragmaticengineer.com/feed) · [One Useful Thing feed](https://www.oneusefulthing.org/feed) |
| Can we check a feed body against a permitted original? | On one Creative Commons post, all 17 paragraphs of the page’s article body appeared in order in the feed, followed by one feed-only paragraph. The first HTML `article` element on the page contained only one paragraph. This gives us a positive comparison and a concrete failure case for a simplistic extractor. Check headings, lists, links, media and the final passage as well as paragraph text for each supported source. [Publisher feed](https://creativecommons.org/feed/) · [Compared article](https://creativecommons.org/2026/11/18/five-years-of-ccs-open-culture-program/) · [Publisher licensing terms](https://creativecommons.org/terms/) |
| What about paid or gated articles? | Substack lets the publisher place a preview boundary within a paid post. Its terms restrict scraping and substantial copying or storage. Use the documented feed for syndication and check permission for retaining, copying or sending bodies to AI. When an excerpt is all the app can use, label it and open the canonical publisher URL in the reader’s browser. The publisher handles sign-in and entitlement. [Paid previews](https://support.substack.com/hc/en-us/articles/4407989020308-How-do-I-publish-a-free-preview-of-a-paid-post-on-Substack) · [Substack terms](https://substack.com/tos) |
| Can we read the discussion? | Publishers control participation and can disable comments. Substack’s documented developer API covers public creator information, and its AI connector exposes publisher dashboard data. We found no documented reader integration granting access to arbitrary paid articles or comment threads. A particular post may publish its own discussion URL. Opening that page requires no access to comment text by Reading Inbox. [Comment settings](https://support.substack.com/hc/en-us/articles/360037832711-How-do-I-enable-or-disable-comments-on-my-posts) · [API scope](https://substack.com/api-tos) · [Publisher connector](https://support.substack.com/hc/en-us/articles/50834026608916-How-to-connect-Substack-to-your-AI-Assistant) · [Example publisher discussion](https://newsletter.pragmaticengineer.com/p/how-software-engineering-is-changing/comments) |

These were read-only checks of public sources. All device tests, paid entitlements, provider output quality and source-specific completeness beyond the sample remain unverified.

## Proposed stack and boundaries

| Component | Responsibility |
| --- | --- |
| **React, TypeScript and Vite PWA** | One semantic HTML reader, responsive layouts, browser history, a manifest with icons and a versioned service worker for the app shell and demo assets. Native browser selection, links and keyboard controls suit a text-first product. Flutter or .NET MAUI could add OS integration but would also require Android and Windows packaging and release pipelines. Revisit if a required device flow fails validation. |
| **IndexedDB through Dexie** | Keep subscriptions, entries, reading state, device positions and permitted summary caches local. IndexedDB transactions keep state and cache updates consistent. The demo runs without an account, backend or key. Offer OPML for subscriptions and a separate portable export for saved items and reading state. Browser storage can be evicted or cleared, so a local copy alone is an incomplete backup. [Browser storage and eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) |
| **Same-origin Node.js service with Fastify, from Phase 2** | A small self-hostable service handles public RSS/Atom retrieval, permitted extraction and optional model calls. A static browser-only client cannot depend on cross-origin feed access or hold a provider secret. Neither sampled feed response advertised an allow-origin header. SQLite is sufficient for a single instance’s feed cursors, observed entry metadata and bounded, permitted caches. [Browser cross-origin requests](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS) |
| **Source adapters** | Each adapter maps available source IDs, attribution, revision, body, coverage and permitted uses into the records below, with publisher and discussion URLs when supplied. Start with fixtures, then public feeds. Prefer publisher-supplied bodies. On demand, use Mozilla Readability on linked public HTML only where site terms and publisher permissions allow. Substack uses syndication and publisher links by default. [Mozilla Readability and sanitisation guidance](https://github.com/mozilla/readability#security) |

## Article data model

The fixture adapter writes the same records that a future RSS, Atom or authorised newsletter import would produce. The reader asks for an article by its stable ID. It can render a plain-text email with no web edition as well as a fully formatted feed entry.

| Record | What it preserves |
| --- | --- |
| Article and source item | Give each article a durable ID. Record where each delivery came from and its source-specific key, such as an RSS GUID, Atom entry ID or newsletter Message-ID within the authorised import source. Use a verified canonical URL as a fallback when available. Where both are missing, keep a local import ID. A matching headline alone is insufficient to combine deliveries. |
| Attribution and links | Preserve the original headline, byline as published, publication, publication date if supplied, and optional publisher article and discussion URLs. If the publication date is missing, sort by collection time and label it **Received**. Show the publication as such if the source omits a byline. An email without a public URL can still be read, saved and archived. |
| Source revision | Keep the delivery reference, content hash, sanitised rich body or plain text, coverage and permitted uses together. An edit creates a new revision under the same article ID. A private newsletter copy retains its own access scope even if the same story has a public teaser. |
| AI summary | Store generated text separately, linked to the source revision, summary stage, model and prompt. This lets a claim link back to a passage and lets an edit invalidate the affected cache. |
| Reader state | Key saved, archived and deepest stage by article and reader. Key the last stage and scroll anchor by device as well. A source edit or a feed changing order preserves these records. |

## Live retrieval and content access

Poll subscribed public feeds conditionally using ETag or Last-Modified when supplied. Use backoff, honour retry instructions and retain observed entry metadata after an item rolls off a feed. A running service can poll while devices are closed. With local refresh alone, a publisher’s finite feed window can pass between visits. Surface the last successful refresh and any known gap.

Treat external HTML as untrusted. Limit fetches to public HTTP(S) destinations, recheck redirects, bound response size and time, and suppress scripts and subresource loading while parsing. Sanitise the result, preserving permitted headings, paragraphs, lists, links, images and captions. Generate plain text and versioned passage IDs from that same body.

Track display, copy, retention and AI permissions independently. Mark a body complete only for a publisher-designated full feed, an authorised newsletter that supplies the entire article, or a permitted extraction with verified article boundaries and intact content. Preview markers, missing sections or uncertain coverage lead to an **Excerpt** label, the reason and **Copy excerpt** where allowed. Offer **Open on publisher site** when a publisher URL exists, including when the body is unavailable. For a complete, copy-permitted body, prepare the plain text so **Copy full article text** can write it in a single tap.

## Reading, discovery and discussion

- **Reading depth** progresses from Essence (one sentence), to Brief (one paragraph), to Understanding (three substantive paragraphs covering the argument, evidence and caveats), to Original. A normal first open requests Essence. More detail, Less detail and Read original are explicit actions. Direct Original skips AI and works during a summary failure. Carry the source headline, byline and publication through all four stages. Each generated stage has a visible, screen-reader-accessible **AI summary** label. **Original** identifies the publisher’s text. Disclose excerpt-only input and link to the publisher when the excerpt cannot support more detail.
- **Reading state** records first open, deepest stage actually viewed, and last stage and scroll anchor per device. Unread means never opened. Viewing a summary sets Skimmed. Showing the complete original sets Original opened. Record an external publisher handoff separately because access and completion there are unknown. Saved and Archived are independent flags. Returning to the list restores its position.
- **Recommendations** can use a small catalogue of permitted feeds tagged by topic. Match against follows and explicit More/Less feedback locally. Insert labelled suggestions around the chronologically ordered subscriptions, retain every subscribed entry and explain each suggestion. Use the share of visible placements for the percentage. The proposed 20% default, 0–50% control and approximate three-new-suggestions daily cap are test settings. Sparse candidates yield fewer suggestions. Only subscription entries contribute to the unread count.
- **Reader discussion** is collapsed below the complete Original. Expanding it reveals **View original comments**, which opens that post’s publisher-provided discussion in the normal browser. If only the canonical article URL is known, label it as the publisher’s post where the reader can check for a discussion. If comments are disabled or neither link exists, show that status. The browser profile handles publisher access. **Summarise discussion** becomes available on demand for text the reader legitimately supplies or a permitted integration delivers. Identify which comments were supplied, how many were analysed and any missing coverage. Link to a supplied permalink or identify the numbered input comment. Cover corrections, counterarguments, evidence, identifiable author replies, useful resources and open questions when present.

## On-demand AI, cost and privacy

Use a deterministic fixture provider first. An optional OpenAI-compatible provider can later receive the permitted article passages for the requested depth, or selected comment text for a discussion request. Explain what will leave the device before enabling external AI. Use a faithful, neutral voice and read from the source at each depth. Ask for versioned passage IDs with claims, validate IDs before linking, and mark uncertainty. Test fidelity against a human-reviewed sample before choosing a model.

Key the cache by reader/access scope, article ID and body hash, coverage, stage, provider/model version and prompt version. For discussions include the supplied comment-set hash. Coalesce identical in-flight requests, cache successful results and recheck permission before serving them. Set input/output limits, per-reader and overall spend caps, bounded retries and a clear offline or budget-exhausted state. An available Original and previously cached stages can still open.

Keep credentials in server-side environment secrets or a secret manager. Protect a paid endpoint with authenticated access or a loopback-only single-user service. Exclude secrets from browser bundles, Git and test fixtures. Omit keys, article bodies and comment text from logs. Keep recommendation feedback local and omit engagement tracking. Review provider retention and disclose it before enabling the service. [API key guidance](https://help.openai.com/en/articles/5112595-best-practices-for-api-key-safety) · [Provider data controls](https://developers.openai.com/api/docs/guides/your-data)

At GPT-5.4 mini’s published standard rates of $0.75 per million input tokens and $4.50 per million output tokens, **1,000 uncached Essence opens would cost $2.43**. Requesting all three summaries for every one would total **$9.09**. This illustration assumes 3,000 billed input tokens including instructions per requested stage and 40, 120 and 360 billed output tokens respectively. Opening Original and revisiting a cached stage make zero model calls. Long articles, retries and comment requests add usage. Hosting and taxes are separate. Reprice at provider selection. API billing is separate from a ChatGPT subscription. [Model pricing](https://developers.openai.com/api/docs/models/gpt-5.4-mini) · [Billing guidance](https://help.openai.com/en/articles/9039756-managing-billing-for-chatgpt-and-the-api-platform)

## Cross-device storage and sync decision

In Phase 1, the inbox and reader use one local storage interface with stable record IDs, a versioned IndexedDB schema and transactional state changes. They read back the local result immediately. A later sync service can apply incoming changes through that same interface while the UI continues working offline.

Before Phase 3, compare extending the self-hosted service (control over data, operator handles backups and auth) with managed authentication and Postgres (less operations work, recurring costs and a data processor). Opt-in sync would send subscriptions, independent bookmark/archive changes, reading progress and permitted cached summaries over authenticated HTTPS with per-user access controls. Article bodies and raw comments are excluded from sync by default.

When sync is enabled, write each local change and its queued operation in one transaction. Use operation IDs to make retries idempotent, server revisions to order accepted changes and deletion markers to preserve removals. Merge the deepest stage reached across devices, resolve explicit bookmark/archive changes per field, and keep each device’s resume position separately. Test an offline phone saving an article while a PC archives it and while a subscription is removed. Offer export and deletion before asking readers to trust a hosted copy.

## Platform and licence decisions

Android Chrome and Windows Edge/Chrome support installation from a secure origin. Install UI and sharing vary by browser. A phone accessing a PC’s ordinary HTTP LAN address does not get the localhost exception. Use HTTPS or device loopback for testing, keep a browser-tab path, provide a selectable-text fallback on clipboard denial and a copy-link fallback for sharing. Refresh on open/resume and on request. Background scheduling is browser-controlled. Physical-device acceptance is in the plan. [PWA installability](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable) · [Edge on Windows](https://learn.microsoft.com/en-us/microsoft-edge/progressive-web-apps/ux) · [Clipboard](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard/writeText) · [Background sync limits](https://developer.mozilla.org/en-US/docs/Web/API/Web_Periodic_Background_Synchronization_API)

Both identify GPLv3 licences. Use their interaction ideas as references. Retain required licence notices, credit the authors and meet any source-distribution obligations. If the terms do not fit, use an independent implementation or obtain permission.
